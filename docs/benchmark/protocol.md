# 高难关卡 Benchmark 评测协议

协议修订标识：`pilot-draft-1`。状态：实验设计，尚未执行。范围与关卡入口见 [README](README.md) 和 [stages.md](stages.md)。本文件中的运行上限是开发阶段的起始设置，冻结规则见第 6 节。

## 1. 实验单位与两条轨道

一个场景由“关卡及模式＋固定阵容与练度＋资料包＋观察/操作规则＋预算＋条件”共同确定。每个场景先填写[场景卡](templates/scenario.md)。E 的 attempt 从战前规划启动计起，R 从加载计划和方法专属预处理计起，到规定终止条件为止；准备失败也产生记录。每个 attempt 最多一次全新战斗开局，同一运行中的多个动作或修复事件不是独立样本。

### E：从零规划并通关

解题器获得统一公开资料包、阵容和允许的初始观察，自行生成计划并执行。主结果是单次尝试的合法通关率；战前规划、格式修正、战中修复都计入该次预算。

- 首版只使用 C0 原生关卡条件，避免与 R 轨道的故障实验混为一项指标。
- 不提供参考打法、已有 Copilot、R 轨道的初始计划或其他方法的执行轨迹。
- 每次尝试清除上次战斗的临时记忆、模型会话和自建打法缓存；跨尝试学习不是首版的评测能力。
- 初始计划生成失败、预算耗尽也占用该次尝试。不能只统计成功进入战斗的运行。
- 如以后增加“最多三次试错”的设置，另立场景修订，报告首次和限次成功率及全部累计成本；不能替代单次结果。

### R：共同初始计划下的在线修复

各方法从同一初始计划 `P0`、同一资料包和统一执行前缀出发。`P0` 的生成规则在开发集冻结后，由独立准备流程完成留出关卡适配；在查看四种方法的留出结果前固定计划与哈希。

- `P0` 在每关 C0 下用同一执行器连续验证 3 次合法通关，保存证据；准备成本单列，不计为某一种修复方法的在线成本。
- `P0` 可以作为本轨道的统一输入；它不进入 E 轨道。它的来源、人工参与及验证次数必须公开登记，不能称本轨道为从零解题。
- 从开局重新运行 `P0`，到预登记的动作/事件才启用待比较的修复策略。C0 在对应位置设置无故障的监测点。
- 方法可以在执行前用共同输入建立索引或内部表示，其时间、调用、token 和费用全部计入本 attempt。方法专属预处理不能藏入免费的 `P0` 准备；统一前缀期间不调用策略提前修改计划。
- 首版允许每关固定一个触发点，局限性单列；扩展到多个触发点前先登记采样规则。
- 不假设游戏支持精确内部状态保存、回滚或固定随机种子。相同前缀并不保证相同隐藏状态。

若某个候选无法获得稳定的 `P0` 或可恢复扰动，应按事先登记的资格规则处理，不能依据某个方法的表现挑选更有利的图。

## 2. 输入、观察和执行条件

### 资料与信息边界

允许统一提供地图、部署格、干员属性、敌人资料和可公开核验的关卡机制说明。资料包在方法间逐字节一致，记录来源、时间与摘要；是否提供完整波次表、触发条件必须逐项登记。

解题时禁止检索现成攻略、视频打法、社区作业和 Copilot。参考通关证据、准备日志、隐藏评测标签与后续运行结果保存在解题器不可访问的位置。模型已有记忆的污染风险单列，不作完全排除承诺。

线上只提供规则允许的画面及统一感知输出，不提供游戏内部完整状态、未来随机结果或评测器的故障注入标志。未知字段保留 `unknown`，不填成确定事实。离线“真值”只用于复核，不能悄悄提高某个方法的可见性。

### 共享执行器

- 固定截图、感知、动作校验和局部控制版本，所有方法使用相同配置；同等观察权限不意味着不同策略会产生相同战斗画面。
- 高层动作包括部署、朝向、技能、撤退、等待，以及场景明确允许的游戏内暂停/恢复。动作参数和资源条件先经确定性校验。
- 云模型负责计划与低频调整；本地控制器按同一规则执行已有计划的条件和时序。不能为某个方法额外补上未声明的战术策略。
- 默认 1 倍速。暂停权对所有方法一致，必须使用经验证的游戏内入口；游戏时间、墙钟时间和暂停时间分别记录。暂停期间能否观察、能否操作在场景卡声明。
- `AsstStop` 会清空原生队列，不能充当游戏内暂停或可恢复 checkpoint。SingleStep 完成回报不单独证明动作成功。
- 部署、技能、撤退等关键动作以操作后的画面或可核验状态确认。状态不明的不可重复动作先观察，不因超时盲目重发。

默认每秒采集 2 次观察；统一动作验证流程可追加观察，追加数量与耗时记录。后续只能在开发集调整该策略。原始观察、感知耗时与模型输入分别计量，防止把感知改善误算为规划收益。

### 最小计划记录

这是研究记录要求，不是已经实现的产品 JSON Schema。四种方法经共同执行格式提交动作；原始方法表示也须保留。

| 记录对象   | 最少内容                                                                                  |
| ---------- | ----------------------------------------------------------------------------------------- |
| 行动实例   | 稳定 ID、发生次数、动作及参数、前置/持续条件、预期效果及验证方式、时间窗/截止点、资源需求 |
| 行动状态   | 待执行、下发中、已确认、失败或未知；回报完成与效果确认分开                                |
| 决策依赖   | 前后节点、因果/条件/资源顺序类型、成立依据及来源观察                                      |
| 事件模型   | 事件/条件、已知与未知事实、来源与时间、更新前后版本                                       |
| 已执行历史 | 实际动作与证据、已用费用、部署占用及冷却；不随计划编辑回写                                |
| 修订提交   | 基于哪个观察/图版本、节点/边/参数差异、校验结果、实际激活时刻                             |

共同校验检查动作白名单、DAG 无环性、已知资源约束、不可改写历史和过期版本。未知前提不能视为已满足；需要观察或条件门禁。静态校验通过不代表真实战场动作成功。新计划只在不会产生重复下发的边界激活，过期提交拒绝并保留记录。

## 3. 方法与可编辑范围

四种方法接受相同外部信息、资源历史及预算。共享低层控制器可以评估原有条件，只有相应方法允许修改计划。

| 标识 | 方法         | 允许的变化                                                                         |
| ---- | ------------ | ---------------------------------------------------------------------------------- |
| B0   | 固定计划     | 执行既定节点、条件和等待；开局后不增删计划节点、不修订依赖                         |
| B1   | 参数修复     | 保持节点与依赖结构，允许修改现有节点的目标、时机、阈值和合法参数                   |
| B2   | 全量重规划   | 保留已执行历史，从当前观察重新生成全部剩余计划；可以保留上下文，不要求丢弃已有信息 |
| M    | DAG 增量修复 | 根据失效前提、因果依赖和资源冲突定位影响范围，修改剩余子图；必要时转全量重规划     |

B1 是参数调整基线。若论文要把收益归因于 DAG 表示及依赖定位，还需增加 **B3：顺序计划的反馈修复**，允许插入、删除、重排剩余后缀，使用同等反馈与预算。不能只战胜参数受限的 B1 就宣称优于所有局部修复。

E 轨道的每个 attempt 独立调用同一配置的冻结战前规划器，再交给对应运行策略；规划器只使用 E 轨道允许的输入。它不读取其他尝试的计划，也不使用 R 轨道已验证的 `P0`。每次实际生成的失败、耗时和费用只记入本 attempt，不把一份共享计划或一次生成失败复制为多个独立样本。初始计划质量仍可能存在运行波动，因此用 R 轨道单独隔离修复收益。

方法专属的图构建、检索、缓存和本地计算全部计时。图信息必须来自共同可用输入；如果 M 获得额外标注的依赖图，应作为不同信息条件单列实验。全量重规划保留已执行动作、费用和冷却，不能重置战斗来获得优势。

M 的局部/全局切换阈值在开发集固定，记录每次切换原因、次数和成本；不能只挑局部修复成功的运行报告。

## 4. 条件与触发规则

| 条件 | 操作                                             | 要检验的内容                                       |
| ---- | ------------------------------------------------ | -------------------------------------------------- |
| C0   | 不注入故障，按关卡原生流程运行                   | 完整能力、原生事件适应，以及固定计划的干净运行基线 |
| C1   | 在预登记部署动作进入执行器时，只延迟该次实际下发 | 时序偏差后的资源、动作及依赖调整                   |
| C2   | 在同一预登记位置，只省略一次实际部署下发         | 动作未生效后的检测与恢复                           |

C1 的开发起始幅度为 **3 秒游戏推进时间**；被延迟的动作在下发前重新校验，不把过期指令强制施加到新状态。延迟期间保持游戏推进，不能用游戏内暂停抵消注入。具体触发节点、幅度、执行器行为及测得的实际延迟在场景卡冻结。

C2 丢弃的是一次动作下发，不是观察帧，也不是从计划中永久删除所有同类动作。执行器不得伪造成功：向策略提供正常动作验证能够获得的失败/未知反馈，后续观察也按统一规则进行。评测器知道的注入原因和预期正确答案不额外提供给策略。

两类故障每次运行各只注入一次。触发以 `P0` 的动作 ID、已确认的波次/击杀或阶段事件定义，不按实验开始后的墙钟秒数。每关先验证触发点能够到达、不会发生在已经不可挽回的败局之后，并由独立参考恢复流程证明至少存在一种合法恢复；参考恢复不输入解题器。

### R 的交接顺序

首版采用“统一前缀→处理触发动作→统一验证→策略接管”的执行顺序，隔离注入前的策略差异：

1. 前缀控制器锁定预登记的部署动作及当时状态，尚未启用待比较策略；记录 `trigger_reached`。
2. 暂不下发 `P0` 后续动作。C0 正常下发该动作；C1 阻塞这一次部署下发并保持游戏推进 3 秒（或冻结幅度），再校验后下发或拒绝；C2 省略该次下发。已在游戏中运行的技能和敌人行为照常推进。C1 因串行下发边界也会推迟后续计划接管，这一效果属于已声明条件。
3. 由同一验证器完成该次动作的效果检查。策略尚不能取消、替换、重复提交触发动作，也不能在 C1 阻塞窗口暂停游戏。验证器只输出正常动作验证可得的状态，注入真值留在评测日志。
4. 记录 `handoff` 后启用相应策略，传入相同规则产生的当前观察、实际历史及 `P0` 剩余部分。交接时不得留有稍后自行下发的旧命令；无法确认原生调用已终结时先由共同控制器处理，不能猜测其取消成功。

注入发生、实际下发、统一验证和策略交接各有时间戳。总体恢复耗时从偏差发生算起，方法接管后的耗时另从 `handoff` 算起；不能把共同的注入/验证等待算成某个方法独有开销。首版 R 主要比较共同检测条件下的修复，不据此宣称方法具有更强的故障发现或感知能力。

首版不向 E 轨道注入 C1/C2，因各方法可能选择不同动作序列。以后增加时，必须先定义与策略无关的触发资格，不能只对某种方法更常使用的节点注入。

### 变化分类

| 标签                 | 含义                             | 不可直接推出的结论               |
| -------------------- | -------------------------------- | -------------------------------- |
| `information_reveal` | 原来未知或看错的信息被补全       | 游戏脚本发生了变化               |
| `mechanism_branch`   | 可核验条件使机制进入另一分支     | 该分支不可预知、一定需要结构修复 |
| `timing_resource`    | 时序、费用、占用、冷却等发生偏差 | 关卡机制依赖发生变化             |
| `action_failure`     | 动作被拒绝、遗漏或实际未生效     | 感知模块一定判断正确             |
| `perception_error`   | 观测遗漏、延迟或识别错误         | 真实战场状态同步发生了变化       |

C1/C2 首先属于执行偏差。只有独立证据确认它们触发了机制分支时，才增加相应标签。专门的观测噪声条件和机制分支子集作为后续登记的扩展，不并入首版三条件汇总。

## 5. 单次运行与公平性

1. 校验场景、阵容、版本、资料摘要、预算及授权批次；从全新开局开始，不继承先前尝试的未声明状态。
2. 在“关卡×条件×重复编号”区组内随机交错方法顺序，保存调度种子。该种子只控制实验安排，不冒充游戏内部随机种子。
3. E 轨道运行冻结的战前规划器；R 轨道加载 `P0` 并执行统一前缀。记录任何进入关卡前的失败。
4. 到达触发/监测点时，保存可见状态签名：游戏时间、击杀、费用、生命/保护目标、场上干员、冷却及关键画面；未知值显式保留。
5. 注入规定条件或继续 C0，运行相应策略；所有观察、图修改、校验失败、动作与验证按顺序编号。
6. 达到通关、失败、超时、违规或人工介入终止条件后，保存结局证据与实际成本。
7. 使用预登记判定规则复核；保留异常与无效记录，按第 7 节决定是否补跑。

各方法的触发状态可能因隐藏随机性和执行抖动不同。先报告可见差异及到达触发点的比例，再解释方法间结果；这属于受控重复实验，不是完全相同状态下的反事实比较。是否进入相近状态只用于分层分析，不能事后删除不利运行。

## 6. 预算和冻结

以下为开发阶段统一起始设置，不是测得的性能要求。两张开发图校准后形成批次配置；留出结果产生后不得回头修改同批规则。

| 项目             | 开发起始上限/规则                                                           |
| ---------------- | --------------------------------------------------------------------------- |
| 战前/方法准备    | E 战前规划或 R 方法专属预处理最多 180 秒墙钟时间，均计入各自 attempt        |
| 单次模型请求     | 30 秒墙钟时间，重试计入调用数与总时长                                       |
| 每次尝试模型预算 | 20 次请求；累计输入 256,000 token、输出 32,000 token，以先到上限者为准      |
| 单次尝试         | 从 attempt 开始累计墙钟 1,800 秒；战斗累计游戏推进 900 秒，以先到上限者为准 |
| 游戏内暂停       | 累计不超过 180 秒；模型等待始终计墙钟，仅与实际暂停重叠的部分计暂停         |
| 观察             | 默认 2 Hz；共享动作验证可追加，规则固定并计量                               |
| 试错             | 每个预登记 attempt 一次新开局；方法失败不自动重开                           |
| 游戏消耗         | 默认理智、药、源石等消耗额度为 0；演习及其有限额度也逐场景登记              |
| 实际模型费用     | 默认可支出额度为 0；执行批次前另行明确模型与总费用硬上限                    |

模型名称、不可变版本或可获得的版本标识、采样参数、提示摘要、上下文压缩、执行器和感知版本全部冻结。供应商仅有滚动别名时记录调用日期与返回标识，说明版本不可精确复现的限制。

E 和 R 的模型预算各从该轨道开始计量；R 的 `P0` 准备另列。成本同时报告 token、调用次数和按登记价目计算的费用，不能仅用调用次数代替费用。

这份计划不授权真实设备运行、消耗额度或模型请求；这里只确定未来执行时应登记的实验参数。

## 7. 结果和异常判定

主成功条件为：在固定阵容、操作和预算约束内，获得可核验通关结果，并满足场景规定的三星/无失守等目标。演习中若结果画面不展示星级，使用事先登记的等价条件和证据，不能只凭“任务完成”回调判成功。普通通关但确认未满足主目标记 `method_failure`、原因为 `objective_not_met`，普通通关事实作为次要结果；目标证据无法确认则记 `unresolved`。

| 结果                     | 处理                                                                                          |
| ------------------------ | --------------------------------------------------------------------------------------------- |
| `legal_clear`            | 主成功，保存结果及约束证据                                                                    |
| `method_failure`         | 战败、未达主目标、预算内无法取得可执行计划、阶段/attempt 超时或不可恢复的执行失败；计入主分母 |
| `constraint_violation`   | 任意阶段违反预算、阵容、暂停或操作规则；主结果按失败，另记是否曾通关                          |
| `assisted`               | 战中人工修改或操作；主结果按失败，人工介入单列                                                |
| `unresolved`             | 结果或责任无法确定；主结果保守按未成功，并报告数量及敏感性分析                                |
| `invalid_infrastructure` | 有独立证据证明设备断连、外部采集损坏等与策略无关；从有效分母剔除，但在尝试总表保留            |

未激活候选的格式、资源或过期版本校验拒绝只记 `proposal_rejected`，单次请求超时记 `request_error`；均允许在剩余预算内修正或重试，不算实际违规，也不自动终止。合法动作未生效也可以继续修复。只有达到阶段/attempt 硬上限、预算内无法取得可执行计划、战败或预登记不可恢复错误等终止条件，才产生终止方法失败。非法计划被实际激活并执行违规动作则按实际违规记录。

分别记录通关、目标达成、实际违规、人工介入、终止方法失败和基础设施异常等事实，再生成最终结果：已确认的违规优先于人工介入，其次是已确认的终止方法失败；若此前均未发生且主目标已确认，则为合法通关。只有尚无已确认结局或终止方法失败、且独立外部异常确实阻止判定时，才记基础设施无效；其余证据不足记未决。后续断连不能覆盖此前的战败、违规或已确认成功。可恢复的中间错误与终止失败分别记录，不能把纠正成功的草稿拒绝当成整次失败。

执行器在合法动作上的失败通常属于真实任务难度，应保留；发现影响所有方法的工具实现缺陷，则停止批次、保留记录、修复并登记新批次。不能把“方法调用工具后失败”统一归为基础设施问题。

有证据的独立基础设施无效运行最多补跑 1 次，关联原 attempt ID，优先不改变该区组方法顺序。仍无效则保留缺失，不无限补到成功。方法失败、未知归因和未到达触发点不按基础设施原因补跑。

## 8. 指标与分析

### 主要结果

- **E 合法通关率**：合法通关次数 / 全部有效尝试，包含战前失败、人工介入和未决结果。
- **R 受扰后通关率**：C1、C2 分开，以全部有效尝试为分母；未到触发点的尝试也保留。
- **R 条件恢复率**：在故障确实注入且已到达触发点的尝试中，最终合法通关的比例。必须同时给出触发到达率，不能单独用这个条件比例代表总体能力。
- **耗时与成本**：在上述成功率旁报告战前/战中模型调用、token、费用、墙钟、游戏推进时间和暂停时间；不合并为未经验证的加权总分。

### 辅助结果

| 指标                    | 口径                                                                                                                              |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 检测延迟                | 偏差发生到可记录的 `deviation_detected` 事件；共享验证器发现与方法接管后识别分别记录，包含偏差类型、行动及证据 ID，不从思维链猜测 |
| 修复提交延迟            | 偏差发生，到首个通过确定性校验的修订提交；不等同于战场已恢复                                                                      |

| p50 / p95               | 报告具体样本数；小样本仅描述分布。未恢复者标记到终止时刻仍未恢复，不填 0 或混入成功耗时                                           |

先按“关卡×条件×方法”列出原始分子、分母与结果，再给每关等权的汇总及 M 对 B2 的差异。E/R 和 C0/C1/C2 不混为一个通关率。

同图重复运行刻画该配置下的波动，不能视作新增独立关卡；同场多个修复事件不能增加通关率样本数。若报告区间，明确它是运行层区间还是按关卡聚类的区间；只有 6 个留出关卡时，两者都不足以证明对全部高难图的普遍性。首版以逐关结果和描述性差异为主，不预设显著性结论。

成功条件下的耗时可单独报告，但必须同时展示失败、超时和未恢复数量，避免只保留成功样本产生误导。统计分析脚本和任何正式检验方案在查看留出结果前冻结。

## 9. 决策 DAG 修复的证据

每次修复保留：前后图版本、变化依据、预测受影响集合、实际修改集合、资源约束、未改部分仍有效的依据，以及后续动作验证。已执行前缀不可改写成“未发生”，费用和冷却不可随删节点复原。

结构修复需要必要节点/子图或依赖关系的增加、删除、重接。换节点 ID、添加冗余传递边、调整时间参数和重试同一动作，不单独算结构修复。分别记录因果边、条件依赖边和资源调度边，说明变化来自关卡认知还是行动调度。

对影响范围的准确性只能在有独立复核依据的子集上报告；没有完整战场真值时，不宣称得到了精确的受影响节点全集。复核尽量隐藏方法名称，争议和未知保留。
