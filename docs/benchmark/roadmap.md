# Benchmark 实施路线与验收

本路线先完成独立评测，再做方法实验和产品接入。当前仅文档落地；没有已实现的研究执行器、已冻结的真实阵容或已测得的通关结果。

## 当前决定与冻结条件

| 事项                                 | 状态                      | 冻结前还缺什么                                       |
| ------------------------------------ | ------------------------- | ---------------------------------------------------- |
| 高难真实关卡优先、benchmark 先于产品 | 已确定                    | 无                                                   |
| 两条轨道、四种核心方法、三类 R 条件  | 协议已登记                | 开发图验证可执行性                                   |
| 8 个候选与 2/6 分组                  | 见 [stages.md](stages.md) | 实际可进入、模式/额度、固定阵容可解性                |
| 每关固定阵容                         | 规则已定，配置未定        | 实际拥有干员、等级、技能、模组、潜能、信赖及配置证据 |
| 初始计划与触发点                     | 待准备                    | 稳定 `P0`、可恢复性、观察证据和哈希                  |
| 模型、执行器、预算                   | 开发起始设置已登记        | 指定模型与执行环境，在开发集完成校准                 |
| 正式运行批次                         | 未授权、未运行            | 场景冻结、设备选择、演习/消耗及模型总费用额度        |

缺少实际账号条件时，保留明确待核实字段，不替用户虚构阵容或通关记录。

## M0：场景资格核验

交付每关一张[场景卡](templates/scenario.md)，以及关卡资格汇总。

1. 核对候选的关卡 ID、显示编号、模式、地图/关卡数据来源与摘要。
2. 核对实际客户端版本、开放/解锁状态、可重玩方式、演习可用额度和是否要求游戏消耗。
3. 按统一规则固定阵容；参考流程证明配置可解，记录方法与证据，不向 E 轨道泄漏打法。
4. 确认每关的三星/保护目标等成功判据，画面可识别，并核验暂停与时钟规则。
5. 给事件变化贴证据标签；对尚未核实的 Boss/路线/条件分支只列研究候选，不当成既定事实。

验收：2 个开发场景和 6 个留出候选均有来源及资格状态；未通过项按[预定替换规则](stages.md)处理。仅数据存在不算资格通过。

## M1：独立执行与记录底座

研究入口与产品 UI 解耦，可以复用设备租约和已有控制能力；不等待完整 Agent 产品化，也不另建产品后端。

- 明确实验需要的最小能力：读统一资料、截图/感知、受限动作、游戏内暂停、动作后验证、双时钟、结构化计划和不可改写的事件记录。
- 先探明选定控制接口在固定核心/资源版本上的真实行为。若使用 SingleStep，先核验参数契约、队列及回报；不能仅凭文档假设支持。
- 研究规划与日志优先采用 TypeScript / 固定 Bun，原生设备调用复用 C++ worker 与共享租约边界；模型只输出受校验动作，不获得任意命令入口。
- 设计独立的数据根、运行 ID、停止和超时规则。不能让产品服务与实验同时控制同一设备，也不能替换活动 worker 引用的文件。
- 用无游戏、无模型密钥、无付费调用的离线夹具验证记录关联、预算、扰动和判定逻辑。合成结果只证明底座逻辑，不进入真实关卡通关率。

验收：记录能够追踪“观察→计划版本→动作→实际验证→结局”；失败和未知不伪装为成功；重复运行不继承未声明记忆。这里列的是待开发任务，当前文档没有实现这些接口。

## M2：开发集校准

只在两张开发图上调整提示、图表示、切换阈值、观察频率、预算及扰动幅度。可先登记 R 轨道 `2 关×4 方法×3 条件×1 次 = 24` 个评测槽位进行流程试验；E 轨道另外登记 `2×4×1 = 8` 个槽位。

上述 32 个槽位只是计划工作量，不代表已执行，也不包含场景资格验证、`P0` 准备或基础设施补跑。独立基础设施异常可能使实际有效尝试数减少，不能保证每格都有有效结果。

验收重点：

- 四方法均能使用同一信息和执行接口，B0 的既定条件调度与 B1 的参数修复边界明确。
- C0 能确认干净运行；C1/C2 能注入一次并得到真实状态证据，至少存在合法恢复途径。
- 关卡仍具有规划压力，固定配置没有因为数值优势而消除所有关键决策；压力说明来自参考执行与机制证据。
- 预算足以让对照完成有意义的决策，同时有可执行上限；任何调整都保留理由，不能依据留出集成绩校准。
- 图修改、观察错误、动作失败和资源冲突能够分开复核。

若当前控制器无法可靠执行固定计划，先解决控制与验证问题；此时尚不能从通关失败判断规划方法优劣。

## M3：冻结试验配置

在查看方法的留出表现前保存一份不可混淆的批次清单，记录提交与内容摘要：

- 关卡/模式/客户端/数据源、阵容规则与各关阵容、资格和替换记录。
- E 战前规划器、四方法实现、提示和模型配置；感知、执行、观察、暂停及动作校验规则。
- R 的 `P0` 准备规则、各关 `P0`、C0 稳定验证、触发点、故障幅度与参考可恢复性。
- 次数、随机交错顺序、预算、费用上限、成功/失败/无效判定、人工介入及补跑规则。
- 指标、汇总和分析脚本；任何额外基线或消融的预登记范围。

留出场景的独立资格准备允许核验可解性，但准备轨迹不用于修改待比较的方法。团队无法隔离准备与研发角色时，如实披露这一限制。

验收：冻结材料足以让另一位开发者判断某次尝试是否符合协议。缺少必要项则保持草案状态，不以空哈希或占位值冒充冻结。

## M4：留出集可行性试验

| 轨道       | 规模                    | 预定评测槽位 |
| ---------- | ----------------------- | ------------ |
| R 在线修复 | 6 关×4 方法×3 条件×3 次 | 216          |
| E 从零通关 | 6 关×4 方法×C0×3 次     | 72           |
| 合计       | 两轨分别分析            | 288          |

这是完成场景资格和开发校准后的预定槽位数，不包含参考解、`P0` 验证、开发试验和基础设施补跑。每个槽位最多因独立基础设施无效补跑 1 次，实际有效 n 可能少于 288，原始尝试数也可能更多；都须报告。执行前按模型配置估算费用和真实演习额度；额度不足时，在产生留出结果前登记完整且对称的缩减方案，不能运行后只保留有利单元。

按关卡/条件区组随机交错四方法。记录到达触发点时的可见差异，不承诺精确回放。中途发现工具缺陷或模型版本改变时保留旧批次，以新修订继续，不覆盖旧结果。

验收：有完整尝试总表，失败、未决、基础设施无效和补跑均可追溯；没有人工补操作后的“自主成功”，也没有把多次动作计为多个通关样本。

## M5：结果与论文主张审查

先交付逐关、逐条件的结果、失败分类和成本曲线，再讨论整体趋势。六张留出图和三次重复是探索性规模，不能据此保证显著性、代表性或论文可发表。

| 观察到的证据                     | 可以进一步讨论的问题                                     |
| -------------------------------- | -------------------------------------------------------- |
| 通关率更高，但更多成本           | 在对应预算下的效果与成本取舍                             |
| 相近通关率下开销更低             | 恢复效率；“相近”的容忍范围须预登记，不能凭不显著认定等价 |
| 有必要子图/依赖修改的完整证据    | 决策 DAG 结构修复                                        |
| 有机制条件分支及事件模型变化证据 | 事件模型更新与决策修复的关系，限定于核实子集             |
| 仅延迟、遗漏后恢复有效           | 执行偏差下的计划恢复能力                                 |

若要归因于依赖结构，增加协议中的 B3 强顺序修复基线；可在开发集预先设计“去掉资源冲突传播”“去掉因果定位”“始终全局修复”等消融，统一预算并登记额外工作量。不能在看到留出结果后挑最有利消融作为预设证据。

进一步的样本扩展、功效分析或正式统计检验，根据试验中测得的差异和方差另立新计划；不将同图重复次数当作关卡覆盖的替代。

## M6：产品接入

方法和评测接口稳定后，再把计划提案、权限、持久编排、预算、人工接管与产品 typed transport 接通。真实设备仍使用共享控制权与既有原生进程边界；研究结果不自动代表三平台产品已验收。

这一步不阻塞 benchmark 的场景、协议与方法工作，也不把研究执行器当成产品 mock 或自动 fallback。
