# 应用与独立组件更新

本文描述 `feat/atomic` 当前源码。应用、MaaFramework SDK 和游戏资源分别安装与更新；本分支不检查、下载、加载或分发 MaaCore。旧发行版行为和验证事实在相应历史段落保留，不代表本分支已经发布。

在「设置 → 更新」选择 Maa Verge 的「正式版」或「预览版」。MaaFramework 只安装兼容清单固定的稳定版本，游戏资源独立按官方 MaaResource 来源检查；后两者没有可切换的应用发行频道。

## 频道与更新行为

| 对象         | 版本来源与行为                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| Maa Verge    | 默认预览频道；正式频道选择项目 GitHub Releases 中非预发布、无 SemVer 预览后缀的版本，预览频道选择正式与预览中版本号最高的已发布版本。 |
| MaaFramework | 固定兼容清单中的稳定 SDK，当前为 `v5.14.3`；上游新版本不自动成为可安装候选。                                                          |
| 游戏资源     | 固定官方源码与 OCR 模型底包叠加 MaaResource 完整包，不按应用或 SDK 版本跳过资源检查。                                                 |

应用草稿不参与检查；版本按 SemVer 比较，`beta.10` 高于 `beta.2`。切回正式频道时，已安装的较高预览版继续保留，不自动降级；切换应用频道取消旧频道候选。SDK 与资源保留各自已验证上一版本，可在对应通道显式回滚，不恢复旧核心或旧核心／资源组合。

Maa Verge 的「启动时检查应用更新」默认开启，只控制联网检查，不会自动下载。发现新版后选择「下载更新」，切换页面不影响下载。签名通过且更新包与清单写盘完成后，选择「安装并重启」，询问是否立刻更新：

- 「立即更新并重启」会停止当前任务、工具和连接，取消后台组件作业，关闭本地服务后调用安装器；正常安装完成后重新启动。未执行计划和业务数据保留，不自动继续游戏操作。
- 「下次启动时更新」或关闭确认框会继续使用当前版本；下次打开时先从本地恢复更新包，复核安装位置、平台/安装器、版本、登记大小与签名，再自动安装。这一步可离线执行，也不受「启动时检查应用更新」开关影响。

Maa Verge 应用、MaaFramework 和游戏资源三条通道共用固定 Bun 上的内置 HTTP 下载器与「设置 → 更新 → 下载代理」，统一使用自动、手动 HTTP/HTTPS 代理或直连模式。自动模式在代理无效、不可达或传输失败时尝试直连；手动模式失败显示错误并保留可恢复数据，不自动绕过所填代理。版本选择和安装流程仍分别管理，代理选择与系统网络边界见 [组件运行时](maacore-runtime.md)。

当前开发源码还提供「设置 → 更新 → Mirror酱」，三通道共用一个 CDK。Mirror酱用户端高速下载为付费服务，官方免费来源继续保留。应用对应 `maa-verge`：Windows EXE、macOS DMG、Linux AppImage 需与官方资产版本、大小和摘要一致，Rust 继续校验绑定内容与版本的 minisign 签名。macOS 应用内更新只接受对应架构的签名 DMG；清单缺失时提示手动安装或等待新版本，不回退 `.app.tar.gz`，旧归档缓存也不能安装。详情及第三方声明见 [Mirror酱说明](mirrorchyan.md) 和 [NOTICE.md](../NOTICE.md)。

应用下载支持安全断点续传：缓存绑定固定来源 URL、版本、大小和摘要，以 HTTP Range / If-Range 核对远端内容后继续；内容身份不能确认时重新下载。临时网络故障和空闲超时默认最多进行三轮请求，重连前分别等待一秒、两秒，并从原始固定 URL 重新请求；自动模式可在代理失败时另尝试直连。切换页面不会取消下载，取消或正常退出保留可恢复分片。应用内版本回滚仍不支持。

三条更新卡片在实际发起下载后显示「下载来源：Mirror酱」或「下载来源：官方源」。该提示来自下载链路的 `downloadSource`，不由 CDK 是否填写或开关是否启用推断；未知来源不显示。Mirror 版本、大小、摘要或下载校验失败而回退时，提示随实际传输改为官方源。切换页面、解压、校验和准备完成后保留本次来源；重新检查或开始新下载时清除旧标记。

HTTP 下载暂存于当前数据根的 `updates/app/downloads`，已签名安装候选保存在 `updates/app`，默认是程序目录的 `config/updates/app`，开发环境是 checkout 的同一路径；遵循自定义数据根。传输完成后由 Rust 复核登记大小、版本和 minisign 签名，签名通过才把包写入独立文件并同步磁盘，再原子提交安装清单。下载分片与未通过签名的文件不会成为启动安装候选。Framework 与游戏资源分别使用不可变版本目录，在设备执行、控制会话及原生操作结束后切换。

Framework 与资源各自显示下载、解压、校验、待生效及激活结果，切换页面后仍可从常驻通知查看。SDK 校验固定版本、文件清单与真实原生加载；资源校验完整静态快照，并在激活前通过无 Controller 的 Framework 探针复核。设备忙时等待空闲，活动文件不原地覆盖；SDK 切换会关闭旧 Controller 并用新版本重建原有连接，重连失败单独报告。下载或探针通过不等于真实游戏行为已验收。

资源的文件摘要缓存只在当前服务内保留，核对文件标识、大小及修改时间等元数据后才复用，变化时重新读取；缓存最多保留八套版本，重启或淘汰后重新读取。校验、回滚及切换仍须经过对应内容和原生门禁。完整目录、模型基线、旧资源只读迁移及 SDK 生命周期见[独立组件与游戏资源](maacore-runtime.md)和[MaaFramework 更新](framework-updates.md)。

启动安装先于本地服务、自动连接和调度。立即安装不等待组件下载结束或已有 RPC 的长时读锁；本地服务先通过 EOF 正常退出，五秒后仍未结束则强制收尾。Windows 还核对并等待本实例的服务、更新作业及原生 worker 退出，保留共享 ADB 和其他应用实例，无法确认退出时保留更新包并重启恢复应用，不继续替换占用文件。macOS/Linux 的强制收尾和真实升级仍需在对应宿主验收。

调用安装器前先持久化本次安装尝试。安装失败、取消或中断后再次打开旧版时，不会反复自动安装；旧版正常启动并在更新页面保留已验证包，可手动重试。重新选择「下次启动时更新」可以安排一次新的自动尝试，无需重新下载；只关闭确认框不会重置失败标记。只有新版本实际启动且版本号已达到候选版本后才清理缓存；改变应用更新频道会取消原频道候选。损坏、缺失或验证失败的缓存拒绝安装，继续打开应用并允许重新检查、下载。Windows 安装器成功启动后由其负责安装和重开应用；当前 Tauri 更新器无法获知安装器后期取消或失败的结果，这种情况下可手动重新打开旧版重试。

## 平台安装方式

| 平台/安装方式                      | 应用内安装                                                                    |
| ---------------------------------- | ----------------------------------------------------------------------------- |
| Windows x64 NSIS EXE               | 下载同类 EXE，签名校验后退出并运行安装器                                      |
| Windows x64 ZIP                    | 从发行页下载完整 ZIP，退出并备份配置后手动更新                                |
| 旧 Windows x64 MSI                 | v0.1.3-alpha.1 起停止提供 MSI，须备份、卸载旧版后手动迁移 EXE / ZIP           |
| macOS Apple Silicon / Intel `.app` | 只下载对应架构的签名 DMG，验证并替换应用包后重启；缺少签名 DMG 时提示手动安装 |
| Linux x64 AppImage                 | 在 AppImage 环境中更新当前 AppImage 并重启                                    |
| 旧 Linux DEB / RPM                 | 后续发行不再提供此类安装包，须手动迁移到 AppImage                             |
| 开发构建、未识别的安装方式/架构    | 可以检查发行版本，禁用自动下载安装                                            |

自动安装仍要求应用位置可写或安装器获得所需权限。macOS 签名/公证和 Windows Authenticode 发布者签名与下文的更新签名是不同机制，目前没有完成这些系统发行签名的配置与验收。

### Windows 离线组件与完整 ZIP

当前 `feat/atomic` 的 Windows EXE 安装向导只有默认勾选的 **MaaResource（完整游戏资源与 OCR 模型）** 一项，不随附 MaaCore 或 MaaFramework SDK。资源已包含在 EXE 内，安装时无需联网下载资源；取消后可在应用中按需安装。Framework 始终在应用内独立安装。应用内更新的 `/UPDATE` 安装保留现有组件，不再次导入随包资源。

**历史行为：** 已发布的 v0.1.3-alpha.1 Windows 向导曾提供默认勾选的 MaaCore（含基础资源）和 MaaResource 两个可选项，后者依赖前者；完整 ZIP 也曾携带这两套组件。这是该版本的安装行为，既有标签、安装包和发行记录保持不变，不能用作本分支的载荷说明。

应用内更新直接复用这份完整 EXE，无需另向 Mirror酱上传增量包。主程序下载并验证后，关闭本实例服务与 worker，通过安装器 CLI 的 `/P /UPDATE /R` 执行原地更新并重启；原应用启动参数由更新器传递。普通双击 EXE 仍运行完整安装向导。这里是下载完整包后的原地更新，不是只下载文件差异的二进制增量传输。

当前完整 ZIP 包含应用、服务、原生 worker 与完整游戏资源；不包含旧核心或 SDK，首次运行仍需独立安装 Framework。完全解压至可写目录后运行 `Maa Verge.exe`，系统仍须具有 WebView2 Runtime。它不注册系统卸载器或快捷方式，也不运行 EXE 自更新；升级时先退出、备份 `config/` 与作业文件，再使用新版 ZIP。不要在归档内直接运行。

资源来源由 `tools/windows-components.lock.json` 固定：官方 MAA 源码资源与模型底包，加上固定 MaaResource 提交及其大小、SHA-256。源码底包在实际下载后记录归档摘要，不把提交标识称为预先锁定的归档 SHA-256。构建复用生产安全提取、完整资源合并和静态内容校验，拒绝原生库、增量包及模型指针；载荷采用资源专用 `formatVersion: 2`。

资源放入程序同级 `MaaResource/generations/` 的不可变目录，保存普通版本清单；服务取得数据根租约并校验后登记，激活前仍需 Framework 原生探针。安装器不写业务数据库、不覆盖同名 generation，已有活动、待生效及自定义目录不会被随包旧版本替换。不再写新的 `runtime/bundled-components` 副本，旧资源布局保留安全导入；旧核心目录只作为可读资源来源保留，不加载或清理其中二进制。

Windows 完整卸载清理默认 MaaFramework、MaaResource 及旧随附载荷，保留配置、自定义目录和旧 MaaCore；应用内升级保留组件。当前独立目录与旧资源迁移说明见[组件目录](maacore-runtime.md#下载与安装目录)。

## macOS 签名与首次放行

后续签名发行只提供完整 DMG，不再生成 `.app.tar.gz` 更新归档。新客户端使用与 Mirror酱相同的完整 DMG：验证整个 DMG 的 minisign 签名后，只读挂载，复制固定的 `Maa Verge.app`，再复核应用标识、版本、可执行文件架构和系统签名；卸载映像后才原子替换已有应用。新版启动且旧更新进程已退出后，按绑定安装位置和目标版本的收据清理旧应用包；进程仍存活时延后清理。准备或校验失败会保留旧应用与候选包，安装位置不可写或文件系统不支持原子交换时停止安装。配置默认在 `.app` 同级；自定义数据根位于待替换的 `.app` 内时拒绝自动更新，须先迁出数据。

DMG 本身仍是可完整安装的映像，可按原方式拖拽安装；`.dmg.sig` 用于自动更新信任校验。仅支持 `.app.tar.gz` 的旧 macOS 客户端须手动安装一次新版 DMG，之后才能使用新的应用内更新。新客户端拒绝旧归档及其安装缓存；历史发行版没有签名 DMG 时明确提示手动安装或等待新版本。2026-10-31 核查的 v0.1.2 与 v0.1.3-alpha.1 清单均没有 `-dmg` 目标，不能作为新客户端的 macOS 应用内更新候选。

macOS 当前的 MaaFramework 与 MaaResource 默认保存在 `~/Library/Application Support/Maa Verge/` 下各自文件夹，不随 `.app` 替换。卸载请使用「设置 → 关于 → 卸载 Maa Verge」；正常关闭服务并取得独占组件租约后，将当前应用及这两个默认组件目录移到废纸篓，保留配置、任务、执行记录、自定义目录、设备锁和旧 MaaCore 目录。无法确认退出、共享占用或保留数据安全时拒绝继续；部分失败会报告已移动项目并恢复应用。Finder 直接删除 `.app` 不触发组件清理。目录及旧资源迁移边界见[组件目录](maacore-runtime.md#下载与安装目录)，此入口仅适用于 macOS 安装版。

当前源码及后续发行版最低支持 **macOS 15（Sequoia）**，覆盖 Apple Silicon 和 Intel。已有发行版的历史系统要求见各版本说明。

macOS 默认使用免费的 ad-hoc 本地签名，不需要 Apple Developer 付费账号或新增 GitHub Secrets。Tauri 配置显式设置 `bundle.macOS.signingIdentity: "-"`，在生成 DMG 及更新签名前封装整个 `.app`；Bun 服务和 C++ worker 保留各自的签名与权限。只签主程序或子进程、没有 `.app` 的资源封装，会导致系统报告应用「已损坏」。

本地签名可以验证应用包完整性，但没有 Apple 认可的发布者身份与公证。首次安装时，先把应用从 DMG 拖到可写的安装目录，尝试打开，再按系统提示到「系统设置 → 隐私与安全性」选择「仍要打开」。应用需要用户明确放行；CI 不修改全局 Gatekeeper 设置，也不承诺未公证下载可以直接打开。

### 历史 v0.1.1 签名问题与处理

以下为 2026-10-24 起针对旧版的核查与处理记录，保留当时发行事实，不作为当前 Framework 分支验收。

已发布的 **v0.1.1 macOS 包确有资源封装缺失**，不是单纯的未知开发者提示。2026-10-24 核对 Apple Silicon DMG 的官方 SHA-256 与映像校验均通过，而 `codesign --verify --deep --strict` 返回 `code has no resources but signature indicates they must be present`。修复已随 [v0.1.2 正式版](https://github.com/DeathofBrain/maa-verge/releases/tag/v0.1.2) 发布，两种 macOS 架构均通过最终 DMG 安装、窗口与包内服务启动、退出清理及更新归档一致性检查；既有发行资产保持不变。

已经下载 v0.1.1 的用户，建议退出旧版并手动安装 v0.1.2 对应架构的 DMG。若仍要临时使用 v0.1.1，先从项目 Release 校验 `SHA256SUMS.txt`，退出应用并复制到安装目录，再在终端只补签这一个应用并验证签名；以下路径须替换为实际位置。该命令不使用 `--deep` 重签，保留三个子进程的权限：

```sh
codesign --force --sign - "/Applications/Maa Verge.app"
codesign --verify --deep --strict "/Applications/Maa Verge.app"
```

随后按系统提示放行。如果系统仍阻止此已核验的应用，可仅移除该应用的下载隔离标记，再打开；不关闭系统安全检查：

```sh
xattr -dr com.apple.quarantine "/Applications/Maa Verge.app"
```

### 当前构建校验

v0.1.2 起由 `tools/verify-macos-bundle.mjs` 强制验证 `.app` 的资源封装和包内子进程签名；该发行版有三个子进程，当前源码移除 aria2 后保留 Bun 服务和 C++ worker。普通 CI 验证本平台合成打包夹具；发行 CI 的两种 macOS 架构运行 `node tools/smoke-macos-install.mjs`：校验最终 DMG、只读挂载并复制到临时安装目录，仅对测试副本模拟放行，用独立的数据、设备锁、日志和 Foundation 用户目录启动真实窗口与包内服务，验证原生退出及无进程残留。自动连接与自动更新在启动前关闭；已有 Maa Verge 实例存在时拒绝测试。

发行 CI 额外传入 `--require-updater`，要求完整 DMG 具有绑定包内容与版本的有效更新签名，并核对安装副本与 DMG 内应用的主程序、资源封装和子进程字节一致；不依赖已删除的中间 `.app`，不再要求或解开专用更新归档。任何检查失败都不能进入资产收集和上传。失败报告保存在 `build/macos-install-smoke/report.json`。这覆盖安装后启动与退出，不代替最低 macOS 版本、首次系统放行界面和真实游戏验收。

## 信任与版本边界

应用只从 [DeathofBrain/maa-verge](https://github.com/DeathofBrain/maa-verge/releases) 查询已发布版本，再读取所选标签自己的 `latest.json`。清单、平台/架构/安装器对应文件名、版本和 GitHub 资产登记必须匹配；包下载只跟随官方 GitHub 附件 CDN 的 HTTPS 重定向。元数据最多 4 MiB，单包最多 1 GiB，下载核对登记大小并限制停滞时间。

发行列表、`latest.json` 与更新包的 HTTP 传输通过桌面宿主专用 RPC 委托 Bun，复用 `createComponentFetch`、`downloadArchive` 和已保存的下载代理设置。前端桥拒绝该宿主请求；Bun 限定官方来源并自行选择下载暂存路径，不提供任意网址下载或任意路径写入接口。Rust 保留仓库、平台、资产大小和版本验证；签名通过后的缓存提交、安装尝试标记、离线启动恢复与安装继续由 Rust 持有。

桌面内置 Tauri 更新公钥，要求 minisign 签名同时绑定包内容与版本；下载完成和安装前分别验证，缺失/错误签名、错误架构、安装器错配或版本回退均拒绝安装。`SHA256SUMS.txt` 供手动校验，不能替代更新签名。业务库不随应用安装回滚。

## 历史版本迁移

以下保留旧版从 v0.1.0 升级到 v0.1.2 的路线，适用于当时的安装与更新器；当前可用发行及安装说明请以[公开发行页](https://github.com/DeathofBrain/maa-verge/releases)和各固定标签文档为准，不把 `feat/atomic` 开发行为套到旧安装包。

[v0.1.0](https://github.com/DeathofBrain/maa-verge/releases/tag/v0.1.0) 的 GitHub 元数据标记为预发布，包含七个平台安装包及校验文件，没有内置应用更新器，也没有签名更新清单/更新包。用户需要手动安装一次 [v0.1.2 正式版](https://github.com/DeathofBrain/maa-verge/releases/tag/v0.1.2)，之后才能使用应用内更新。v0.1.1 已内置更新器，可在「设置 → 更新」获取 v0.1.2；macOS 旧版无法启动时请直接安装新版 DMG。保留旧标签与产物，不覆盖重发。

## 准备新发行版

`.github/workflows/release.yml` 有两个入口：推送版本标签 `v*`，或在 Actions 中选择 **Prepare signed application release** 并填写一个已存在的标签（用于补跑）。工作流先解析标签指向的提交，拒绝不存在的标签、版本不一致、缺失的发行说明和任何已有 Release（含草稿），再等待该提交的 Checks 成功；随后在四宿主构建、签名并校验资产，最后创建 GitHub **草稿**，不会自动公开发布。本分支的 Framework 改造尚未因此发布；后续发行仍需先提交新的版本号，并保留既有标签与资产。

1. 同步根 `package.json`、桌面/服务 `package.json`、`tauri.conf.json`、Cargo 包版本及相应锁文件，并编写 `docs/releases/v版本号.md`。标签必须为 `vMAJOR.MINOR.PATCH`，可带有效预览后缀；发行版本不接受 build metadata。
2. 合并版本与发行说明提交，先确认该提交的完整 Checks 已通过，且 `full-validation` 成功。`main` 推送和手动 Checks 运行执行完整检查；`dev` / PR 的精简检查不能用于发行。标签必须指向这个提交；发布流程不会为失败、被取消或缺失的完整 Checks 构建。
3. 确保 Actions secrets 已配置 `TAURI_SIGNING_PRIVATE_KEY` 与 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。本轮已在项目仓库配置，公钥保存在 Tauri 配置中；私钥和密码须独立加密备份，不得提交。后续版本沿用此密钥，直接换公钥会使旧客户端无法验证新包。
4. 推送本次新版本标签，或对尚无 Release 的已有标签手动补跑并填写该标签。含预览后缀的标签自动生成预发布草稿，不再单独选择 `prerelease`。构建从 secrets 读取签名材料；普通不带密钥的 `pnpm build` 仍可生成未签名测试安装包，不可直接作为自动更新发行版。
5. 构建期间标签被移动或出现并发 Release 时流程失败；草稿资产生成或校验失败会删除本次草稿并保留标签，修正后可重跑。检查草稿中的全部 **11 项附件**及发行说明，核对构建与安装验证记录后再手动发布。发布前客户端看不到草稿。

完整 Checks 运行中的等待上限为 30 分钟；没有完整运行时最多等待 5 分钟。若该提交只有精简检查、没有运行、运行被取消或失败，先执行 `gh workflow run ci.yml --ref <标签>` 并等待 `full-validation` 成功，再补跑 Release。

CI 和普通 `pnpm build` 只构建 Windows EXE / 完整 ZIP、macOS Apple Silicon / Intel DMG、Linux AppImage 五个完整安装包；不再生成 DEB、RPM 或 macOS `.app.tar.gz` 等专用更新归档。完整发行附件集合为这五个安装包、EXE / 两个 DMG / AppImage 的四个 `.sig`、`latest.json` 与 `SHA256SUMS.txt`，共十一项。签名和清单是更新及校验元数据。`latest.json` 只包含 `windows-x86_64-nsis`、`darwin-aarch64-dmg`、`darwin-x86_64-dmg`、`linux-x86_64` 四个目标，直接引用完整安装包；完整 ZIP 仅列入 SHA-256 清单，不作为应用更新包。

发布工具 `tools/app-updater-release.mjs` 在收集及生成清单时验证真实签名、签名版本和完整产物集合。macOS 构建使用既有更新签名密钥，通过官方 Tauri signer 为完整 DMG 追加版本绑定签名，不改变 DMG 内容或 Mirror酱上传流程。各平台带空格的原始产品名严格匹配后统一为 `Maa-Verge` 文件名；复制重命名保留包内容与签名，重复或无法识别的安装包拒绝收集。发行资产解析与校验集中在 `tools/release-assets.mjs`，校验当前十一附件集合，同时兼容既有八附件、含 MSI 的十八附件、EXE / 完整 ZIP 的十七附件及带完整 DMG 签名的十九附件集合，拒绝不完整的混合版本；安装包通过 GitHub Releases 与既有 Mirror酱分发。

当前验证范围见 [开发状态](STATUS.md) 和 [Mirror酱真实下载验证](mirrorchyan-verification-2026-10-31.md)。合成检查与 Windows 构建不能代替真实升级安装、macOS/Linux 宿主和最低系统验收。
