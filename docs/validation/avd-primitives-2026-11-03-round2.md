## 3. 日常流程

### 任务领奖

**从游戏主页开始的任务流程通过本次已测分支，并实际领取了免费日常奖励。** 返回的日常结果为 `changed: true, matched: obtained, verified: true`，周常为 `changed: false, claimVisible: false, verified: true`。奖励弹层关闭后回到任务页，共 214 个记录步骤。

入口先等待一秒，再以新帧核对主页和任务入口；只点击一次，并保留官方入口的切页等待。领奖前等待页面稳定，覆盖层阻止输入，关闭后复核。没有通过重复点击掩盖页面过渡。

证据：`award-from-home.json`、`award-from-home-after-52.png`。本轮没有逐项审计奖励种类和数量，不依据账号余额反推奖励明细。

### 登录

本轮发现并处理了两类问题：主页左侧“限时签到／许愿墙”卡片被当成弹窗标题；冷载入实际持续时间超过原有等待窗口。主页同帧命中后，仅排除官方活动卡片区域内的标题，真正弹窗仍要求已审阅标题与关闭证据。START 输入得到确认后提供最多 60 秒的只读等待，其他局部窗口保持 20 秒，且受 120 秒根期限约束。出现未审阅覆盖层不会续期或重放输入。

换网后的两次记录必须区分：

1. 从应用冷启动进入：初始窗口先观察到未知画面、资源载入，约 20.398 秒才读到 START；由于窗口已到期，返回未知，**未发出点击**。这次完整冷启动不计通过。
2. 独立确认已在 START 后发起新流程：实际只点击一次 START，约 47 秒后读到主页并完成稳定检查；但 JSON 后续重复执行主页稳定检查，最终在第八个步骤附近耗尽根期限。**游戏到达主页，流程仍为未知**，没有自动重放。

重复稳定等待随后修复：注册器为每个顶层执行签发新的不透明根身份，子调用继承；仅在同一根、同一实际输入修订下复用“主页稳定等待已完成”。后续 JSON 步骤仍读取新帧并检查覆盖层和载入。任何非主页、读取异常、输入修订变化或独立根执行都会失效；缺少可靠修订的端口不启用缓存。没有放宽 120 秒根期限，也没有跳过 JSON 的十步上限。

最终版本重新启动游戏、只读等待并确认 START 后再次执行：仅点击一次 START，约 **52.7 秒**观察到主页，但第四次稳定复读结束已约 **60.8 秒**，超过 60 秒局部窗口，因此返回未知，未自动重放。随后独立观察确认为主页。该次真实复测说明冷登录等待边界仍不足以覆盖本环境的全部载入／稳定耗时，**冷登录仍未通过**；不能用相同网络下前次较快的 47 秒记录替代。

最后从独立确认的主页执行完整登录 JSON，**26.8 秒、330 步，`succeeded / verified: true`**，没有任何点击步骤。保留十步新帧核验的情况下，同根稳定缓存已实际生效。这只证明“已在主页”路径与重复等待修复，不是冷登录成功。

证据：`startup-home-title-false-positive.json`、`headful-cold-login.json`、`network-cold-login.json`、`network-start-page-login.json`、`final-login-start-confirmed.json`、`final-start-page-login.json`、`final-home-login.json`。状态诊断只记录规则命中、状态与时限，不输出账号 OCR。

当日重新登录未再次出现月签到、活动公告、许愿等首次登录弹窗。因此，相关关闭逻辑的合成回归不等于这些真实分支已经验收。

## 4. 基建：从错误假设改为可核对证据

### 实际人数与完整名单

第一轮把名单页顶部当作已选人数／容量来源，真实页面没有该字段。本轮将可见卡片、完整已选名单和房间面板人数分开：

- 入房后在明确的房间面板读取“进驻人数 x/y”，记录目标、帧、实际进驻人数和容量；设施理论上限仅用于拒绝异常值。
- 未修改的名单只能在同次入房人数证据下，收集足够数量的唯一已选姓名，才声明完整。
- 清筛选、翻页和选人后的状态不能继续沿用原进驻人数冒充当前已选总数。缺少可靠修改后计数时，在清空或选择之前停止。
- 已打开的面板不会再次点击切换关闭；名单完整卡片锚点与导航均有有界只读等待。

控制中枢真实面板读到 **5/5**，会客室读到 **2/2**。面板 OCR 的无关前缀不参与人数语义；心情 `20/24`、可见卡片数量或占位格不作为容量。

修复面板重复切换后，会客室 `read_room` 首次成功返回完整名单 2 人、容量 2。新增官方姓名字典后再次复测，控制中枢与会客室均返回 `succeeded / verified: true`：

| 房间     | 同次面板实际人数／容量 | 完整名单                 | 复核                               |
| -------- | ---------------------- | ------------------------ | ---------------------------------- |
| 控制中枢 | 5/5                    | 5 名官方字典精确匹配姓名 | 对照截图的五张选中卡片一致；286 步 |
| 会客室   | 2/2                    | 2 名官方字典精确匹配姓名 | 对照截图的两张选中卡片一致；270 步 |

控制中枢曾在入房过渡和名单卡片过渡期间过早读取失败；随后稳定画面能读到 12 张卡片、其中 5 张选中，但原始姓名含边界标点及 OCR 误识别，不能据此声明 5 人姓名全对。

本轮新增同代资源 `battle_data.json` 的简中官方姓名核对，保留 `rawName`、`nameVerified` 与来源摘要。仅允许边界标点去除后与官方姓名完全相等；不做模糊猜名。未知姓名不能进入完整名单、点击选择或训练角色路径。

最终结果的 `nameSource` 指向同资源代 `resource/battle_data.json`，SHA-256 为 `dc2020a6f5651ada0a3f3c61ed2c744ea31fefa0407dc29ed64b948265a3e939`。不将同屏未选中的其他卡片也计为完整名单通过。

额外尝试会客室 `prepare_roster`，请求保持原有两人名单。它在重置筛选的候选识别阶段返回“当前画面未命中任何候选规则”，未清空、未选人、未确认；随后截图仍为原两人选中。因此本次只证明该失败没有越过选择／提交边界，**没有实际触达修改后人数保护，不计作该保护的实机通过**。筛选入口适配仍需修复和实测。

证据：`control-panel-ocr.json`、`reception-panel-ocr.json`、`reception-read-fixed.json`、`control-read-final.json`、`control-roster-stable-observe.json`、`final-control-dictionary-read.json`、`final-reception-dictionary-read.json`、`final-prepare-count-guard.json` 及对应截图。

### 提交边界

准备凭据改为 provider 内部一次性不透明 ID，绑定资源、输入修订与准备证据，拒绝篡改、复用和跨 provider。宿主输入修订只在实际输入尝试时推进，普通观察、纯调用以及 Schema／帧门禁拒绝不推进。

原生模拟器手动点击或游戏自行跳页不会推进宿主修订，因此确认还必须在实际输入前的新帧核对当前设施与完整位置；无法证明重复设施位置时停止。训练受训者也不能只信准备时的选中证据。相关提交保护仅使用合成行为验证，**本轮没有真实确认基建名单**。
