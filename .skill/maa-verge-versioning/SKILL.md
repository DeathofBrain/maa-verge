# Maa Verge 版本号管理

以 [语义化版本 2.0.0 中文规范](https://semver.org/lang/zh-CN/)为依据。区分 SemVer 的要求与本项目的发行约定；以下 `0.y.z` 策略、频道命名及文件同步属于项目约定。

## 确定范围与基线

- 阅读 [AGENTS.md](../../AGENTS.md)、[PLAN.md](../../PLAN.md)、[开发状态](../../docs/STATUS.md)，检查已有差异，只修改本次版本任务涉及的内容。
- 区分“建议版本号”“检查一致性”“实际升版”：建议或检查任务只读；用户要求升版时直接完成本地文件同步和验证。版本修改本身不包含 commit、push、创建或移动标签、上传资产、创建或发布 Release；已有明确授权按其范围执行。
- 从根 [package.json](../../package.json) 读取当前应用版本，核对工作区、Tauri 和 Cargo；通过本地标签、提交差异及实际 Release 证据区分源码版本、已发布预览版和已发布正式版。`git tag` 不能证明 Release 已公开，`docs/STATUS.md` 也不能代替发布证据。
- 用户指定基线时遵从；否则以目标发行线最近已发布版本为比较基线，结合当前未发布版本判断是否只是继续同一预发布序列。缺少远端证据时明确基线来源，不把本地最新标签直接称为最新正式版。
- 对变更集评估兼容性，不能仅凭提交前缀、提交数量、开发日期或分支名计算版本。文档或内部重构不必自动升版；若随新构建发行，依据实际兼容性和交付目的决定级别。

## 先定义公共兼容性承诺

SemVer 要求精确说明公共 API。Maa Verge 的评估范围包括被用户或集成方依赖的契约接口、配置与计划导入导出格式、CLI 参数、持久化数据的读取/迁移、已承诺的用户行为和平台支持。以当前文档和契约为证据，指出本次具体影响的承诺，不把所有内部实现都当作公共 API。

- 删除或重命名公共入口、增加必填字段、收窄合法输入、改变既有语义、移除承诺的平台支持，均检查是否破坏兼容性。
- 新增可选字段或能力，只有旧调用方、旧配置与数据仍能按原约定工作时才算兼容；存在自动迁移不等于任意方向都可兼容，说明升级与降级边界。
- 缺陷修复如果同时破坏已承诺的行为，按实际影响判断，不能只因名称为“修复”就判为 patch。不明确的承诺先列出证据和缺口；仅在其会改变版本结论且无法从仓库确定时询问用户。

## 选择升版级别

对于 `X >= 1`，对本次发行全部变更取最高级别：

| 变更                                          | 级别  | 示例            |
| --------------------------------------------- | ----- | --------------- |
| 任何不兼容的公共 API 修改，包括移除已弃用能力 | major | `1.4.7 → 2.0.0` |
| 兼容的新功能，或将公共 API 标记为弃用         | minor | `1.4.7 → 1.5.0` |
| 仅兼容的缺陷修复                              | patch | `1.4.7 → 1.4.8` |

主版本递增时次版本和修订号归零；次版本递增时修订号归零。新功能发行可以包含修复，不因多个修复累加多次 patch。依赖更新按它带来的能力与兼容性影响分类，不按依赖自己的 major/minor/patch 照搬。

### 初始开发阶段与 1.0.0

SemVer 允许 `0.y.z` 阶段快速变化，不承诺公共 API 稳定，也未强制此阶段的不兼容修改升到 `1.0.0`。本项目在没有其他既定发行策略时采用：

- 兼容修复递增 patch；新增功能、弃用或不兼容修改递增 minor 并将 patch 归零，不兼容项仍须明确记录。
- 已有目标版本的预发布只是在完善同一交付范围时，保持 `X.Y.Z`，按下面的预发布规则推进；若新范围需要更高级别，重新评估目标基号。
- `1.0.0` 表示公共 API 形成，不能仅因功能较多、构建成功或去掉预发布后缀自动升级。结合正式使用、稳定接口和项目验收证据判断，保留未完成的平台与真实设备验证边界。

## 预发布、构建信息与排序

- 核心版本必须为三个非负整数 `X.Y.Z`，禁止前导零。拒绝 `1.2`、`01.2.3`、`1.2.3.4`；不要静默补齐或清洗输入。Git 标签前缀 `v` 不属于版本号本身，应用文件写 `1.2.3`，项目标签写 `v1.2.3`。
- 预发布为 `X.Y.Z-标识符[.标识符...]`；标识符非空，只允许 ASCII 字母、数字和连字符。纯数字预发布标识符禁止前导零：`alpha.1` 合法，`alpha.01` 非法。
- 新序列建议使用 `alpha.N`、`beta.N`、`rc.N`，从 `1` 开始是项目命名建议，并非 SemVer 强制。保持目标基号，按范围推进，例如 `0.2.0-alpha.1 → 0.2.0-alpha.2 → 0.2.0-beta.1 → 0.2.0-rc.1 → 0.2.0`；阶段含义与功能冻结要求由本次发行计划决定。
- 从预发布转正式版时，移除该目标基号的后缀即可，不额外递增 patch；仍须满足正式发行条件。已经发布的正式版不能再以同一基号预发布作为升级，应选择下一个目标基号。
- 历史 `alpha1` 是合法的单个字母数字标识符，不能强制改名或按数字尾号排序。例如 `alpha10 < alpha2`，且 `alpha.2 < alpha1`；切换命名时必须比较完整候选版本，保证预期升级方向，必要时使用更高目标基号。
- SemVer 允许 `+build`，构建标识符同样非空且只含 ASCII 字母、数字和连字符，纯数字可以前导零，如 `1.2.3+001`。构建信息不参与优先级：`1.2.3+abc` 与 `1.2.3+def` 同级，不能靠更换构建信息让更新器识别新版。
- 比较时依次按数值比较主、次、修订号；同一基号下，正式版高于预发布。预发布逐段比较：纯数字按数值，数字低于非数字，非数字按 ASCII；相同前缀下，字段多者更高。不得用整串字典序、`localeCompare` 或发布日期替代 SemVer 优先级。

```text
1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-alpha.beta < 1.0.0-beta
  < 1.0.0-beta.2 < 1.0.0-beta.11 < 1.0.0-rc.1 < 1.0.0
1.9.0 < 1.10.0
```

### 本项目当前工具边界

- [tools/release-assets.mjs](../../tools/release-assets.mjs) 的 `releaseVersion()` 是实际发行标签入口：要求 `v` 前缀、完整标签最长 128 字符，允许合法预发布，**不接受 `+build`**。标准合法与项目可发行需分别判定；不为一次升版放宽校验器或更改资产命名协议。
- [services/backend/src/release-version.ts](../../services/backend/src/release-version.ts) 提供组件版本解析和 `compareReleaseVersions()`；[services/backend/src/app-release.ts](../../services/backend/src/app-release.ts) 提供应用版本比较与频道候选选择。先读当前实现与测试，按场景复用，数字比较避免精度丢失，不新增一套排序逻辑。
- 应用正式频道排除预发布，预览频道允许预发布；频道不改变版本优先级，也不代表可以自动降级。不要假定任意新预发布格式都已通过各平台打包验收。

## 同步应用版本

以当前仓库实现为准重新核对；当前统一应用版本涉及以下文件，值不含 `v`：

| 文件                                                                                   | 位置与处理                                                                  |
| -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| [package.json](../../package.json)                                                     | 根 `version`，应用版本来源                                                  |
| [apps/desktop/package.json](../../apps/desktop/package.json)                           | 桌面工作区 `version`                                                        |
| [services/backend/package.json](../../services/backend/package.json)                   | 应用服务工作区 `version`                                                    |
| [packages/contracts/package.json](../../packages/contracts/package.json)               | 契约工作区 `version`，当前随应用同步                                        |
| [packages/agent/package.json](../../packages/agent/package.json)                       | Agent 工作区 `version`，当前随应用同步                                      |
| [apps/desktop/src-tauri/tauri.conf.json](../../apps/desktop/src-tauri/tauri.conf.json) | 顶层 `version`                                                              |
| [apps/desktop/src-tauri/Cargo.toml](../../apps/desktop/src-tauri/Cargo.toml)           | `[package].version`，不要替换依赖版本                                       |
| [apps/desktop/src-tauri/Cargo.lock](../../apps/desktop/src-tauri/Cargo.lock)           | 用 Cargo 同步本地 `maaverge` 包版本，审查差异，不手改生成文件或顺带升级依赖 |

- 避免全仓字符串替换：历史发行说明、旧版迁移说明、测试夹具及第三方组件可能有意使用旧版本。
- [pnpm-lock.yaml](../../pnpm-lock.yaml) 是否变化取决于实际依赖解析；单改应用版本不一定会改变它。需要更新锁文件时使用项目固定 pnpm 和 Cargo，保留锁文件并检查无关依赖变动，不手工伪造同步。
- 常规应用升版不连带修改 `.bun-version`、`.node-version`、MaaCore 版本、资源提交标识、NDJSON `protocolVersion`、JSON Schema 的版本字段或 SQLite 迁移序号。它们按自身兼容性与迁移任务独立演进；资源不必采用 SemVer，核心同版也不能跳过资源更新。
- 更新 [开发状态](../../docs/STATUS.md) 中的源码版本与验证记录，但只有实际公开发布后才更新“已发布版本”。准备发行说明时使用 [maa-verge-release-notes](../maa-verge-release-notes/SKILL.md)，写入 `docs/releases/<tag>.md`；实际需要修改用户 README 时再读取 [maa-verge-readme](../maa-verge-readme/SKILL.md)。

## 验证与交付

在仓库根目录按任务范围验证：

```bash
# 将示例标签替换为本次目标；只读取本地配置，不创建标签或发布。
node tools/app-updater-release.mjs check --tag v0.2.0-alpha.1

# 版本标签与发行配置逻辑发生变更时，运行现有合成专项。
node --test tools/tests/release-assets.test.mjs tools/tests/app-updater-release.test.mjs
```

- 上述 `check` 只核对根包、桌面、服务、Tauri、Cargo.toml 与标签参数一致；另行核对 contracts、agent、Cargo.lock。该命令不会确认标签存在、发行说明齐备、Checks 成功或安装包可用，不把它的通过写成完整发行验收。
- 仅改版本文件时执行版本一致性和修改范围的格式检查；涉及契约、排序、迁移或更新行为时，再按相关入口运行定向及项目要求的检查。格式化仅覆盖支持的源文件，不格式化生成锁文件。
- 用 `git diff --check` 及逐文件差异确认未改动无关版本，保留其他贡献者的改动；简要报告基线、目标、升版理由、同步文件、已运行检查和待验证项。只请求建议时，报告结论而不写文件。
- 已发行内容保持不可变：不重打或移动已发行标签、不覆盖旧资产、不直接改旧版本说明来掩盖问题。发现误标或破坏兼容后，在新版本修复并说明影响；仅变更构建元数据不能代替新版本。
- 用户授权进入发行流程时，再使用 [maa-verge-ci-release](../maa-verge-ci-release/SKILL.md) 核对当前工作流、标签与非空说明、Checks 及签名草稿门禁；本 skill 的版本检查不能取代该流程。
